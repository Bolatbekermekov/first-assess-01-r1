## 1. Способ защиты и его условия

### 1.1 Что именно воспроизводится

Порядок записи в CLI: `mkdir(out_dir)` → `open(out_dir)` по пути → запись двух отчётов через дескриптор. `mkdir()` не возвращает дескриптор, поэтому каталог открывается заново по имени. Процесс с правом переименования в родительском каталоге может между `mkdir` и `open` убрать созданный каталог и поставить на его место свой **пустой**. CLI открывал подставленный каталог, писал в него отчёты (там контактные данные) и печатал `REPORT_CREATED`. Это и воспроизвела проверка.

### 1.2 Разбор: какую подмену можно обнаружить, а какую нет

Ключевой факт POSIX: связать результат `mkdir` с открытым объектом нельзя — нет атомарного «создать и открыть каталог», `mkdir` не возвращает дескриптор, `renameat2(RENAME_NOREPLACE)` и `O_TMPFILE` для каталогов в стандартной библиотеке Python недоступны. Значит, абсолютной гарантии «это ровно тот каталог, что создал mkdir» дать нельзя.

Но подмену можно разделить по тому, **кто** её делает, и для настоящей угрозы гарантия есть:

| Кто подменяет | Чем отличается подставленный каталог | Можно ли обнаружить |
|---|---|---|
| Другой пользователь (общий родитель, например `/tmp` без sticky bit) | Принадлежит **другому** uid: чужой пользователь не может создать каталог, принадлежащий нам | **Да** — проверкой владельца |
| Тот же пользователь, но каталог оставлен открытым для группы/прочих (типовой `mkdir` с umask по умолчанию → `0o755`) | Имеет биты доступа группы/прочих | **Да** — проверкой режима |
| Тот же пользователь (или root), пустой каталог `0o700`, принадлежащий нам | Ничем не отличается от созданного нами | **Нет** |

Настоящая граница безопасности — другой пользователь. Процесс от нашего же имени и так внутри нашего доверия: он может прочитать или изменить отчёты напрямую, независимо от CLI. Поэтому необнаружимый остаток лежит вне модели угроз.

### 1.3 Условия, которые требуются решению

- **Проверка владельца** предполагает, что файловая система присваивает созданный каталог нашему `euid`. Это верно для локальных дисков и tmpfs; на отображающих владельца сетевых монтированиях (NFS `root_squash`/`all_squash`, часть sshfs/SMB) созданный нами каталог может числиться за другим uid, и тогда штатный запуск вернёт `IO_ERROR`. Проверено, что владелец = `euid` на: APFS (macOS), tmpfs и ext4 в контейнере, bind-mount `fakeowner` Docker (`logs/22_*`).
- **Режим каталога.** out-dir теперь создаётся `mkdir(out_dir, 0o700)` вместо режима по umask (обычно `0o755`). Отчёты содержат контактные данные, поэтому доступ только владельцу уместен (решение A14 в `LIMITATIONS.md` обновлено). `umask` может только убавлять биты, поэтому созданный каталог никогда не получает биты группы/прочих.
- **Windows.** Ветка без `dir_fd` использует только `O_EXCL` по полному пути и этих проверок не делает. На Windows не запускалось.

## 2. Исправление в рамках текущего контракта

`assess_workbench/cli.py`:

1. Каталог создаётся `os.mkdir(out_dir, 0o700)` — владельцу, без доступа группе/прочим.
2. После открытия (с убранными хвостовыми `/`, `O_DIRECTORY | O_NOFOLLOW`) и **до записи** вызывается `_is_own_empty_directory(dir_fd)`. Каталог принимается, только если одновременно:
   - принадлежит нам: `fstat(dir_fd).st_uid == os.geteuid()`;
   - закрыт для группы и прочих: `S_IMODE(st_mode) & 0o077 == 0`;
   - пуст: `os.listdir(dir_fd)` пуст.
   Иначе — `IO_ERROR`, ни один отчёт не пишется.
3. Сохранены все ранее работавшие проверки: `mkdir(exist_ok=False)` (существующий путь → `OUTPUT_EXISTS`), `O_NOFOLLOW` и снятие хвостовых `/` (symlink → отказ), `O_DIRECTORY` (не-каталог), запись через дескриптор каталога с `O_EXCL | O_NOFOLLOW`, и финальная проверка `os.path.samestat(fstat(dir_fd), lstat(path))` (подмена после открытия → `IO_ERROR`).

Код ошибки — `IO_ERROR`: по §7 контракта это сбой записи после создания собственного каталога. Созданные файлы не удаляются (контракт разрешает оставить частично созданный каталог и запрещает удалять чужие пути). Формат успеха и всех ошибок не изменился. Нормативные файлы байт-в-байт прежние.

### 2.1 Что теперь гарантируется и что нет

**Гарантируется** (POSIX, ветка с `dir_fd`, на ФС с обычной семантикой владельца):
- отчёты не пишутся в каталог, принадлежащий другому пользователю (закрывает подмену чужим пользователем полностью);
- отчёты не пишутся в каталог, открытый группе/прочим, и в непустой каталог;
- symlink на месте `out_dir` не разыменовывается, в том числе при `/` в конце пути;
- `REPORT_CREATED` печатается, только если после записи путь `out_dir` указывает на тот же каталог;
- CLI ничего не перезаписывает и не удаляет.

**Не гарантируется:**
- **Тот ли это каталог, что создал `mkdir`,** если подмену делает тот же пользователь (или root) пустым каталогом `0o700`, принадлежащим нам. Такой каталог неотличим от созданного; это вне модели угроз (см. 1.2). Зафиксировано тестом `test_identical_owner_only_directory_swapped_in_cannot_be_detected` (A16).
- **Отображающие владельца ФС** (NFS squash и т. п.): штатный запуск вернёт `IO_ERROR` (см. 1.3).
- **Windows:** проверки не выполняются (см. 1.3).

## 3. Регрессионные тесты

`tests/test_candidate_cli.py::DirectorySwapTests`. Подмена выполняется внутри процесса ровно в окне: двойник `os.mkdir` создаёт каталог по-настоящему и тут же заменяет его; двойник `os.open` вмешивается перед созданием первого отчёта. Чужое владение моделируется подменой `os.geteuid` (другой пользователь не может создать каталог, принадлежащий нашему euid, поэтому несогласие `geteuid` с владельцем каталога — точная модель этого случая).

| Сценарий | Ожидание | Какая проверка ловит |
|---|---|---|
| symlink после `mkdir`, для `out`, `out/`, `out//` | `IO_ERROR`, цель symlink пуста | `O_NOFOLLOW` + снятие `/` |
| каталог, доступный группе/прочим (`0o755`), после `mkdir` | `IO_ERROR`, out-dir пуст | режим |
| каталог другого владельца после `mkdir` | `IO_ERROR`, out-dir пуст | владелец |
| непустой каталог (`0o700`) после `mkdir` | `IO_ERROR`, его содержимое не изменено | пустота |
| пустой каталог `0o700` того же владельца | известный предел A16: `REPORT_CREATED`, ничего не перезаписано, ровно два отчёта | — |
| каталог переименован после открытия | `IO_ERROR`; новый каталог по пути пуст, отчёты — в созданном | `samestat` |

**Красный/зелёный.** Новые тесты владельца и режима запускаются на коде возврата R2 (`git archive` коммита `9a76d1a`, сверка с его `RETURN_MANIFEST.json`) — они падают (`logs/17_r3_regression_tests_on_r2_code.txt`), и проходят на R3 (`logs/18_r3_regression_tests.txt`). Прочие сценарии из таблицы уже проходили на R2 и остаются зелёными.

**Мутации** (`logs/15_mutation_smoke.txt`): удаление каждой из трёх проверок (`владелец`, `режим`, `пустота`), создание каталога доступным группе/прочим и возврат к `makedirs(exist_ok=True)` обнаруживаются тестами.

**Конкретное поведение успешного запуска** (`logs/22_r3_output_directory_is_owner_only.txt`): out-dir создаётся с режимом `0700` и принадлежит текущему пользователю.

**Не проверено:** настоящий параллельный процесс (подмена моделируется внутри процесса в точной точке окна; попасть в окно в несколько микросекунд из другого процесса можно лишь случайно) и Windows.

## 4. Запрос решения по контракту (не применён)

Проверка указала: запрос 2.5 не согласован, самостоятельно менять нормативные требования не нужно. Поэтому контракт не изменён. Для завершения прошу решения по одному пункту — он касается **условия эксплуатации**, а не алгоритма.

Проверка владельца закрывает подмену чужим пользователем, но на ФС без семантики POSIX-владельца (NFS `all_squash`/`root_squash`, часть sshfs/SMB) она отвергнёт штатный запуск с `IO_ERROR`. Выбор — чья это ответственность. Предлагаемая формулировка условия эксплуатации для §7 (если будет принята):

> Родительский каталог out-dir должен быть доступен на запись только вызывающему пользователю либо иметь sticky bit, и файловая система должна присваивать создаваемый каталог эффективному пользователю процесса. При этих условиях CLI не следует symlink, не перезаписывает и не удаляет существующие пути, не пишет в непустой каталог, в каталог другого владельца и в каталог, открытый группе/прочим, и сообщает об успехе, только если out-dir по-прежнему указывает на созданный им каталог. Подмена пустым каталогом `0o700`, выполненная тем же пользователем или root между созданием и открытием каталога, не обнаруживается и считается вне модели угроз.

Обоснование и альтернатива:
- Текущая реализация выбирает **безопасность по умолчанию**: на отображающей владельца ФС она ошибётся в сторону `IO_ERROR`, но никогда не запишет отчёты в чужой каталог. Это согласуется с §7 (сбой записи → `IO_ERROR`) и не меняет форматы.
- Если владелец контракта предпочтёт **доступность** на таких ФС, проверку владельца можно смягчить (например, оставить только проверки режима и пустоты). Это снова откроет подмену чужим пользователем на общих каталогах без sticky bit. Такое изменение не вносил — оно требует решения владельца контракта.

Проверку владельца в R3 **реализовал**, потому что она закрывает настоящую угрозу «запись в чужой каталог» в рамках текущего контракта и не трогает нормативные файлы; формулировка выше нужна лишь чтобы зафиксировать соответствующее условие эксплуатации, когда оно будет согласовано.
