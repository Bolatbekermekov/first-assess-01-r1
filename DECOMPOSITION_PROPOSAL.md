# DECOMPOSITION_PROPOSAL — FIRST-ASSESS-01, возврат R2

Это предложение кандидата. Оно не назначает работу, не присваивает production task ID и не подключает код к FIRST. Оценок трудозатрат и календарных обязательств здесь нет. Части повторяют границы модулей возврата, поэтому каждую можно принять отдельно по её собственным тестам.

## Карта частей

```text
A. Парсер входа ──────────────┐
B. Валидация полей ──> C. Группировка ──> D. Отчёт ──> E. HTML
                                            │
F. CLI и безопасный вывод ──> (A, D, E через публичный API)
G. Адаптер FIRST (опционально, отдельный контракт) ──> (A или D)
```

Общая зависимость всех частей — `contract.py` (поля, статусы, коды, лимиты, `TypedDict` отчёта) и `errors.py` (`WorkbenchError`). Это общий словарь, а не отдельная часть: он меняется только вместе с контрактом.

## A. Парсер входа (`load_rows`)

- **Назначение.** Превратить байты JSON или CSV в список сырых рядов, не оценивая их содержимое.
- **Вход и выход.** `bytes`, формат `"json" | "csv"` → `list` (элементы JSON без изменений; для CSV — `dict[str, str]` в каноническом порядке полей).
- **Ошибки.** `WorkbenchError` с кодами `INVALID_DATA`, `INVALID_FORMAT`, `INPUT_TOO_LARGE`, `INVALID_ENCODING`, `INVALID_DOCUMENT`, `TOO_MANY_ROWS`, строго в этом порядке.
- **Зависимости.** Только stdlib и общий словарь.
- **Критерии приёмки.**
  - порядок ошибок и включительные пределы (10 485 760 байт, 10 000 рядов);
  - один BOM;
  - JSON: дубли ключей на любой глубине, `NaN`/`Infinity`, `RecursionError`;
  - JSON (R2): целое любой длины загружается с точным значением. Результат не зависит от `sys.set_int_max_str_digits` и `sys.setrecursionlimit`, а настройки процесса не меняются;
  - CSV: заголовок, число ячеек, пустые записи, malformed и quoted cells;
  - `csv.field_size_limit` восстанавливается;
  - исключения без фрагментов входа и без `__context__`.
- **Готовые тесты.** `tests/test_candidate_loading.py` (в том числе `IntegerDigitLimitTests`); `tests/test_candidate_environment.py`; публичные `test_parser_errors_and_precedence`, `test_json_csv_equivalence_and_bom`; `test_json_and_csv_inputs_are_equivalent`.

## B. Валидация и нормализация полей

- **Назначение.** Для одного ряда вернуть либо шесть нормализованных значений, либо коды ошибок в порядке полей.
- **Вход и выход.** `object` → `RowCheck(normalized: NormalizedRow | None, codes: tuple[str, ...])`.
- **Зависимости.** Stdlib (`re`, `unicodedata`, `urllib.parse`) и общий словарь.
- **Критерии приёмки.**
  - общее правило проверяется на исходном значении, пределы — после нормализации;
  - каждая ветка нормализации из таблицы §2 контракта;
  - решения A1–A3, A8, A10 закреплены тестами;
  - нет HTML unescape, URL decode и NFKC.
- **Готовые тесты.** `tests/test_candidate_fields.py`; публичные `test_url_and_control_character_boundaries`, `test_surrogate_text_rejected`, `test_empty_and_invalid_literal_reports`.

## C. Группировка (точные дубли и конфликты)

- **Назначение.** Классифицировать валидные ряды внутри одного набора.
- **Вход и выход.** Последовательность `(row_number, NormalizedRow)` в порядке входа → `dict[row_number, Classification(status, code, duplicate_of_row)]`.
- **Зависимости.** Только тип `NormalizedRow` из части B; от самой валидации не зависит.
- **Критерии приёмки.**
  - ключ `(casefold(name), url, country, language)`, без `source_ref`;
  - любой второй ключ превращает всю группу в CONFLICT;
  - первый ряд — представитель;
  - пустое и заполненное значения различаются;
  - нет fuzzy-сопоставления;
  - сложность O(n).
- **Готовые тесты.** `tests/test_candidate_grouping.py`; инварианты с независимым оракулом в `tests/test_candidate_properties.py`; публичные `test_late_conflict_updates_entire_group`, `test_rejected_row_does_not_poison_group_and_no_fuzzy`.

## D. Сборка отчёта и JSON-сериализация

- **Назначение.** Проверить scope и список рядов, собрать отчёт `ASSESS_LEAD_REPORT_V1`.
- **Вход и выход.** `rows: list`, `scope: dict` → `Report` (обычный `dict` строго по §4).
- **Зависимости.** Части B и C.
- **Критерии приёмки.**
  - порядок `INVALID_SCOPE` → `INVALID_ROWS` → `TOO_MANY_ROWS`;
  - точные ключи и builtin-типы;
  - `summary` считает ряды;
  - вход не изменяется, общей памяти с ним нет;
  - детерминизм;
  - эталонные отчёты fixtures.
- **Готовые тесты.** `tests/test_candidate_report.py`; публичные `test_literal_golden_and_input_immutability`, `test_scope_and_row_limits`.

## E. HTML-представление

- **Назначение.** Автономный локальный HTML-документ для человека.
- **Вход и выход.** `Report` → `str`.
- **Зависимости.** Только схема отчёта (часть D) и общий словарь. Отчёт можно заменить любым, совместимым по схеме.
- **Критерии приёмки.**
  - полный документ; виден весь результат, ничего не обрезано;
  - REJECTED показывается без исходного входа; пустой набор — явно;
  - экранирование только через `html.escape(…, quote=True)`;
  - белый список тегов и статических атрибутов, без JS, ссылок и внешних ресурсов;
  - детерминизм.
- **Готовые тесты.** `tests/test_candidate_html.py`; публичный `test_html_escapes_visible_data`.

## F. CLI и безопасный вывод

- **Назначение.** Единственная точка файлового ввода-вывода.
- **Вход и выход.** Аргументы командной строки → новый каталог с `report.json` и `report.html`, код выхода и ровно одна строка в stdout или stderr.
- **Зависимости.** Публичный API (части A, D, E).
- **Критерии приёмки.**
  - порядок шагов, ошибка входа приоритетнее `OUTPUT_EXISTS`;
  - `mkdir(exist_ok=False)`, symlink не разыменовывается, в том числе при `/` в конце пути;
  - созданный каталог открывается по пути и должен быть пуст;
  - запись `O_EXCL | O_NOFOLLOW` через дескриптор каталога;
  - успех заявляется, только если после записи путь указывает на тот же каталог;
  - граница A16 (подмену пустым каталогом обнаружить нельзя) и модель угроз — по решению владельца контракта, `docs/R2_REWORK.md`, раздел 2.5;
  - `IO_ERROR` и `OUTPUT_EXISTS`;
  - чтение ограничено `limit + 1` байтами;
  - вход не изменяется, значения пользователя не выводятся, `KeyboardInterrupt` не перехватывается;
  - результат не зависит от настроек интерпретатора и локали.
- **Готовые тесты.** `tests/test_candidate_cli.py` (в том числе `DirectorySwapTests`); `tests/test_candidate_environment.py`; публичные `test_cli_json_csv_and_no_overwrite`, `test_cli_bad_input_creates_no_output_or_input_leak`.

## G. Возможный адаптер FIRST (только предложение)

- **Назначение.** Если понадобится связать модуль с данными FIRST: преобразовать записи из источника FIRST в шесть полей контракта, а отчёт — в формат потребителя FIRST.
- **Почему отдельно.** По `CONTRACT.md` §8 интеграция требует отдельного решения и отдельного контракта. Части A–F о FIRST ничего не знают и останутся неизменными.
- **Вход и выход.** Определяются будущим контрактом. Предварительно: запись источника → `dict` из шести строковых полей (вход части D), либо `Report` → структура потребителя.
- **Зависимости.** Публичный API частей A и D. Production-пространства FIRST подключаются только внутри адаптера.
- **Критерии приёмки (черновик).**
  - сопоставление полей без потери данных;
  - адаптер не меняет семантику статусов и не добавляет разрешений на контакт;
  - не вводит сеть в вычислительные части;
  - собственные тесты на синтетических данных.

## Порядок независимой приёмки

1. Части A, B и C можно принимать параллельно: у них общий только словарь.
2. Часть D принимается после B и C, часть E — после фиксации схемы отчёта D.
3. Часть F принимается последней, на собранном API.
4. Часть G принимается только после отдельного решения об интеграции.

Каждую часть принимают её тестовым модулем плюс подмножеством публичных тестов, перечисленных выше.
