# FIRST-ASSESS-01 R1 — проверочное задание разработчику

Проект: Sales Manager FIRST. Исполнитель: пока не назначен.

Разработайте самостоятельный локальный модуль `assess_workbench`, который принимает синтетические списки потенциальных клиентов из JSON или CSV, проверяет качество полей, нормализует записи, находит точные дубли email и конфликты, выпускает JSON и удобный HTML-отчёт с причинами каждого результата.

Это кодовая проверка кандидата по тематике проекта. Модуль должен запускаться из этого пакета без исходников остальных модулей, доступа к инфраструктуре или получения результатов других разработчиков. Здесь нет реализации решения: предоставлены контракт, данные, тесты приёмки и каркас, который явно возвращает NOT_IMPLEMENTED.

Работа нужна для оценки инженерного мышления, устойчивости к плохим входам, качества кода, тестирования и способности передать воспроизводимый результат. В перспективе принятые части можно выделить в отдельные технические задания. Декомпозиция в этом возврате — предложение кандидата; она не назначает работу и не подключает код к FIRST автоматически.

## Обязательный результат

1. Реальный Python-модуль с API из `CONTRACT.md`, без сторонних зависимостей.
2. CLI для JSON/CSV, детерминированный JSON-отчёт и автономный HTML-отчёт.
3. Собственные тесты сверх предоставленных: границы, ошибочные данные, взаимодействие правил, безопасная работа с файлами.
4. Отчёт о реализации, фактические журналы запуска, ограничения и предложение разделения результата на небольшие независимо принимаемые части.

Изучите `CONTRACT.md` до разработки: это единственный нормативный источник алгоритма. Примеры и тесты его иллюстрируют; прохождение только видимых тестов не заменяет выполнение контракта.

## Границы

Используйте Python 3.12 и стандартную библиотеку. Не нужны PostgreSQL, Docker, Make, CRM, браузер, LLM, API-ключи или реальные контакты. Не добавляйте сетевые запросы, веб-сервер, интерфейс редактирования, авторизацию, постоянную БД, fuzzy matching или скоринг продаж. Данные в fixtures вымышленные.

Синтаксическая валидность и совпадение email не означают, что компания существует, является подходящим покупателем, адрес принимает письма или есть разрешение на контакт. Статус UNIQUE означает только отсутствие другого валидного ряда с таким email в текущем наборе. Не добавляйте outbound/send/qualified разрешения.

## Порядок работы

- CP0: распаковать, прочитать контракт, выполнить `python CHECK_PACKAGE.py` и `python RUN_ACCEPTANCE.py`. В исходном каркасе ожидается честный результат NOT_IMPLEMENTED с ненулевым exit code.
- CP1: сообщить, как устроены парсер, нормализация, группировка и отчёт; существенные неясности контракта перечислить до изменения поведения.
- CP2: реализовать модуль и собственные тесты. Зафиксировать непокрытые случаи и реальные результаты запуска.
- CP3: проверить возврат по `RETURN_INSTRUCTIONS.md` и передать один ZIP со статусом READY_FOR_REVIEW.

Не правьте нормативный контракт и предоставленные приёмочные тесты ради PASS. Если обнаружили ошибку в условии, опишите её отдельно с минимальным воспроизведением. Окончательную приёмку проводит независимый проверяющий.
